## Project Overview

**Oxidus** is a MUD (Multi-User Dungeon) library written in LPC (Lars Pensjö C), designed to run on FluffOS 2019+. It is authored and maintained by Gesslar.

- **Language**: LPC (a C-like scripting language for MUDs)
- **Driver**: FluffOS 2019+
- **Project Type**: Game development framework/library for text-based multiplayer games
- **Documentation**: <https://oxidus.online/>

## LPC Language Characteristics

### File Extensions

- `.lpc` - LPC source files (objects, daemons, commands). **This is the
  extension for all source in this lib — create new files as `.lpc`.**
- `.c` - Legacy LPC source extension. The FluffOS driver still resolves it
  (explicit `.c`/`.lpc` is exact; extension-less names prefer `.lpc` and fall
  back to `.c`), but the lib has been fully migrated and no `.c` source remains.
- `.h` - Header files (defines, macros, includes)

When code needs to probe for a source file on disk, use the `source_file()`
simul_efun (strips any extension, prefers `.lpc`, falls back to `.c`) rather
than hardcoding an extension.

### Key Differences from C

1. **No explicit compilation**: Files are loaded/compiled by the driver on-demand
2. **Object-oriented**: Everything is an object, inheritance with `inherit`
3. **Special functions**: `create()`, `setup()`, `init()` are lifecycle hooks
4. **Data types**: Includes `mapping` (hash/dict), `object`, `mixed`
5. **Arrays**: Called "arrays" but syntax is `string *arr` or `int *arr`
6. **No pointers**: Despite `*` syntax, these aren't C pointers
7. **Built-in functions**: `sprintf()`, `call_other()`, `this_body()`, etc.
   (use `this_body()`, not `this_player()` — see the `/driver-overrides` skill)

### Modern FluffOS Syntax

FluffOS supports more than the classic LPC subset. These are all verified in
this driver and preferred where they read better:

- **Mid-block declarations** (C99 style) — declare near first use; don't wrap in
  a bare `{ }` block just to scope a variable
- **Template literals** — `` `${name} arrives.` `` beats `+=` concatenation
- **Dotwalk on mappings** — `m.key` ≡ `m["key"]`, string keys only (int/object
  keys still need brackets); read *and* write
- **Optional chaining** — `?.` is read-only (illegal as an lvalue)
- **Nullish coalescing** — `??` / `??=` fire on genuine undefined; `||` and `??`
  differ only on `0`
- **Default-argument functionals** — `varargs int f(int x: (: 1 :))`; the
  functional is resolved at the call boundary, the body sees the value
- **async / await / acatch and `promise`** — `async int f()` is typed
  `promise<int>` at every call site; `await` suspends without blocking the
  driver, `acatch` is the suspension-safe `catch`. Applies and command entry
  points must **not** be async — the driver reads their return immediately, so
  a sync entry point calls an async helper without awaiting it. Promises are
  first-class and combinable (`promise_all`, `promise_race`, …) and an async
  body can be asked to give up with `promise_cancel()`. Sync is the default,
  not the fallback. See the `/async-promises` skill

### Common LPC Data Types

- `int` - Integer
- `string` - String
- `float` - Floating point
- `object` - Reference to an LPC object
- `mapping` - Associative array/dictionary: `([ key: value ])`
- `mixed` - Any type
- `void` - No return value
- `<type> *` - Array of type (e.g., `string *names`)

### LPC Syntax Examples

```lpc
// Variable declarations
private string name;
private int *numbers = ({ 1, 2, 3 });
private mapping data = ([ "key": "value" ]);

// Function definition
private varargs int my_function(string arg, int optional) {
  // varargs means optional parameters allowed
  return 1;
}

// Inheritance
inherit STD_OBJECT;

// Preprocessor — only for headers not already pulled in by <global.h>
#include "include/my_module.h"
#define MY_CONSTANT 100
```

## Code Style Guidelines

Full rules live in the `/lpc-coding-style` skill. Highlights:

### Language

Use **Canadian English** everywhere — code, identifiers, comments, strings,
documentation, file names. colour, behaviour, defence, centre, honour,
catalogue, analyse.

### Indentation

- **2 spaces** for indentation (NOT tabs)
- Consistent indentation throughout the file

### Brace Style

- Opening brace on same line as control statement, always preceded by one space
- Closing brace on its own line, unless followed by `else` / `catch`
- **Single-statement bodies take NO braces** — body on the next line, indented
- If any branch of an `if`/`else if`/`else` chain needs braces, all branches get
  them. `switch` is per-case.

```lpc
if(condition)
  do_something();
else
  do_other_thing();

if(condition) {
  do_something();
  do_more();
} else {
  do_other_thing();
}

void function() {
  // code
}
```

### Naming Conventions

- **Functions**: snake_case (`create_account`, `load_account`)
- **Variables**: snake_case (`account_name`, `player_data`)
- **Accessors/mutators**: `query_` and `set_` prefixes, never `get_`
- **Constants/Defines**: UPPER_SNAKE_CASE (`STD_DAEMON`, `MAX_PLAYERS`)
- **Classes**: PascalCase (`ClassGMCP`, `ClassEvent`)
- **Private functions**: do NOT use a `_` prefix — the `private` keyword says it
- **Unused parameters**: `_` prefix suppresses the LSP unused diagnostic
  (`string query_help(object _caller)`) — parameters only, never locals
- **File-globals**: `__` prefix is a soft preference on new globals
  (`private nosave mapping __handlers = ([]);`); leave established names alone
- **Never** name a local the same as a function in scope
- **Files**: snake_case.lpc (`account.lpc`, `string.lpc`)

### Visibility

Every function and file-global carries an explicit `private` / `protected` /
`public`. Default to `private`, and choose by *call mechanism*, not by taste:

- Reached via `ob->fn()` / `master()->fn()` → **`public`**
- Called by an inheriting object as an inherited lfun → **`protected`**
- Called only within the defining file → **`private`**
- Driver applies (`create`, `setup`, `heart_beat`, `valid_*`) → **`private`**;
  the driver ignores visibility, so don't widen them

### Spacing

- NO space between a control keyword and its condition: `if(`, `for(`,
  `while(`, `switch(`, `foreach(`
- NO space between function name and parentheses: `function(args)`
- Spaces around operators: `a + b`, `x == y`
- NO space after unary operators: `!flag`, `++i`
- No trailing whitespace; files end with a single newline; never 2+ blank lines

### Blank Lines

- Blank line **after** a closing `if`/loop/`switch` block, unless the next line
  is itself a closing brace
- Blank line **before** `return`, unless it's the only statement in the block

### Line Width

Don't over-wrap. Most lines land under 80 columns naturally; a 90-column line
in a block of one-liners beats an awkwardly broken one. When a line is genuinely
hard to read, fix it structurally (extract a variable), not with a line break.

### Example from codebase

```lpc
varargs string simple_list(string *arr, string conjunction) {
  assert_arg(pointerp(arr) && uniform_array(arr, T_STRING), 1, "Invalid or missing array.");

  conjunction = conjunction || "and";

  if(sizeof(arr) == 1)
    return arr[0];
  else if(sizeof(arr) == 2)
    return arr[0] + " " + conjunction + " " + arr[1];
  else
    return implode(arr[0..<2], ", ") + ", " + conjunction + " " + arr[<1];
}
```

## Documentation Standards

### LPCDoc Format

This project uses **LPCDoc**, a JSDoc-like documentation system for LPC code.
It is to be called LPCDoc — not JSDoc, and not "JSDoc-like" — in code comments,
documentation, and conversation. See the `/lpcdoc` skill for the full spec.

The description is **bare text**, not a tag, and is followed by a blank ` *`
line before the first tag. Types are mandatory on `@param` and `@returns`.

#### Function Documentation

```lpc
/**
 * Appends a string to another string if it is not already there.
 * If the string is already present, the original string is returned.
 *
 * @param {string} source - The string to append to.
 * @param {string} to_append - The string to append.
 * @returns {string} The original string, with the appended string if it
 *                   was not already present.
 */
string append(string source, string to_append) {
  // implementation
}
```

#### File Documentation

```lpc
/**
 * @file /adm/daemons/account.lpc
 *
 * Account daemon responsible for managing player accounts, including creation,
 * modification, and character associations.
 *
 * @created 2024-08-09 - Gesslar
 * @last_modified 2024-08-09 - Gesslar
 *
 * @history
 * 2024-08-09 - Gesslar - Created
 */
```

The blank lines after `@file`, after the description, and after
`@last_modified` are all required.

#### Common LPCDoc Tags

- `@file` - File path, followed by the file's purpose
- `@param {type} name - Description` - Parameter documentation
- `@returns {type} Description` - Return value documentation (no dash)
- `@type` - Variable/parameter type annotation
- `@overload` - Alternate call signature
- `@errors` / `@throws` - Only when the function calls `error()` / `throw()`
- `@example` - Usage examples
- `@created` / `@last_modified` - Date and author
- `@history` - Change log

`@description` and `@simul_efun` are retired. If you meet them in an old file,
drop the tag and keep the text as the leading description.

#### What Not to Document

Forward declarations, inherit statements, preprocessor directives, and
ubiquitous lifecycle entry points (`main()` in commands, `setup()`,
`mudlib_setup()`, `base_setup()`, `pre_setup_N()`, `post_setup_N()`). File-global
variables need a block only when `@type` gives the LSP shape it can't infer —
objects, structured mappings, classes, or arrays of those. Plain primitives
don't.

Everything else — including `private` helpers — requires a block; the LSP relies
on `@param` types to resolve them. Doc lines wrap at 79 characters.

An LPCDoc block describes what *that* function does. Don't restate a sibling's
internals; a name-disambiguating pointer is fine, a copy of its logic is drift
bait.

## Common Patterns in Oxidus

### Object Lifecycle

`create()` runs `setup_chain()`, which calls, in order:

1. `std_setup()` — the `/std` layer's own wiring
2. `mudlib_setup()` — mudlib-level wiring
3. `base_setup()` — inheritable base wiring
4. `pre_setup_0()` … `pre_setup_4()` numbered hooks
5. `setup()` — **the author's entry point**; this is what you write
6. `post_setup_0()` … `post_setup_4()` numbered hooks
7. the restore chain, then `mudlib_complete_setup()`

`on_destruct()` mirrors it through `unsetup_chain()` (`std_unsetup`,
`mudlib_unsetup`, `base_unsetup`, `unsetup`, …). Virtual objects have a parallel
`virtual_setup_chain()` / `virtual_unsetup_chain()` with `virtual_`-prefixed
steps, and `virtual_setup()` as the author's entry point. `init()` still fires
when an object enters an environment. See [std/object/setup.lpc](std/object/setup.lpc).

### Inheritance Patterns

```lpc
inherit STD_DAEMON;         // For daemon objects
inherit STD_OBJECT;         // For basic objects
inherit STD_ROOM;           // For room objects
inherit __DIR__ "exits";    // For sibling modules within a std/ subsystem
```

### Simulated Efuns

- Located in [adm/simul_efun/](adm/simul_efun/)
- Extend or replace driver functions
- Examples: `append()`, `prepend()`, `simple_list()`, `no_ansi()`
- Sefun source files `#include <simul_efun.h>` at the top
- **Adding, moving, or removing a sefun requires updating its prototype in
  [adm/include/simul_efun.h](adm/include/simul_efun.h)** — that header is a
  hand-maintained fdecls list, sectioned by source file. Nothing at runtime
  catches drift.

### Common Utility Functions

- `nullp(x)` - Check if null/undefined
- `stringp(x)` - Check if string
- `intp(x)` - Check if integer
- `objectp(x)` - Check if object
- `pointerp(x)` - Check if array
- `mapp(x)` - Check if mapping
- `sizeof(arr)` - Get array/mapping size
- `strlen(str)` - Get string length

## Important Considerations

### Includes

`<global.h>` is the driver's global include and is already in scope everywhere.
It pulls in `<mudlib.h>`, `<daemons.h>`, `<colour.h>`, `<dirs.h>`, `<type.h>`,
`<messaging.h>` and more — **never re-include any of those**. Grep
[include/global.h](include/global.h) if unsure. For sibling headers under
`std/<module>/include/`, use the relative form (`#include "include/foo.h"`).

Never put variables in a header. Functions are fine to share via `#include`;
classes require `inherit`. For shared constants, expose a daemon getter.

### Security

- **Permission checks**: Always validate permissions before sensitive operations
- **Input validation**: Validate all user input
- **Encryption**: Passwords must be encrypted (see `$6$` prefix in account.lpc)
- Use `assert_arg()` for parameter validation — prefer a one-line `assert_arg()`
  over an inline `if(...) error(...)` guard
- Oxidus uses the FluffOS **privs** model, not `PACKAGE_UIDS`

### Performance

- **Lazy loading**: Objects loaded on-demand
- **Clean-up**: Use `set_no_clean(1)` for persistent objects
- **Persistence**: `set_persistent(1)`, then `save_data()` / `restore_data()`
  from [std/ext/persist_data.lpc](std/ext/persist_data.lpc) — see the
  `/persistence` skill

### String Operations

- Use simul_efuns for common operations: `append()`, `prepend()`, `chop()`
- `extract()` for substring operations
- Range syntax: `str[0..5]`, `str[<3..]` (last 3 chars)

### Arrays and Mappings

- Arrays: `({ elem1, elem2, elem3 })`
- Mappings: `([ key1: value1, key2: value2 ])`
- Access: `arr[index]`, `map[key]`
- Operators: `+` for concatenation, `-` for removal

## Code Review Rules

The review standard for this repository is
[.claude/skills/lpc-review/SKILL.md](.claude/skills/lpc-review/SKILL.md). Read
it before reviewing anything and follow it as written — it governs what
qualifies as a finding, how scope is bounded, how much to report, the evidence
required before asserting a driver failure mode, and the LPC/FluffOS semantics
most often mistaken for defects. The rules below are the load-bearing ones,
restated so they hold even when that file is not read.

- **Scope findings to the change.** Repository knowledge and unchanged code may
  be used to understand and validate the change; they are not permission to
  review anything else. Report a condition only if the change **created** it. A
  consumer that worked before the change and breaks after it is in scope
  wherever it lives — that is downstream, not adjacent. Pre-existing
  conditions, partial migrations, and code that does not yet match its eventual
  shape are states, not defects. There is no "while you're here" category.
- **Every finding states what the change did to cause the condition.** If that
  cannot be stated as a fact about the diff, the finding does not exist.
  Resemblance to code elsewhere is not evidence.
- **Report every qualifying finding in one pass, strongest first.** There is no
  cap. Withholding real defects to keep the list short turns one round of fixes
  into several.
- **No findings is the expected outcome for most changes**, and is a complete
  review rather than a failed one. Volume is a consequence of the bar, never a
  target, so there is no reason to reach for something to say.
- **Do not raise style, formatting, spacing, naming, or documentation-format
  comments.** Those conventions live in the skills listed at the top of this
  file, and a generic guess at LPC convention will usually contradict them.
- **Ground driver claims in the driver source.** Any claim that FluffOS will
  raise an error, fail to resolve a call, crash, truncate, coerce, or reject a
  path is a claim about `fluffos/fluffos` — read the implementing code rather
  than assuming C defaults. There is no pinned driver version — the image is
  built from whatever upstream FluffOS was at build time — so the driver in
  front of you is authoritative and recent efuns are not suspect for being
  recent.

## Working in this Codebase

1. **Always read before editing**: LPC files may have complex inheritance chains
2. **Respect existing patterns**: Match the coding style of surrounding code
3. **Document thoroughly**: Use LPCDoc format for all functions
4. **Test assumptions**: LPC syntax differs from C in subtle ways
5. **Check includes**: Header files define crucial constants and macros
6. **Understand inheritance**: Many features come from inherited objects
7. **Watch for simul_efuns**: Custom functions that override built-ins
8. **Be mindful of scope**: `private`, `public`, `nomask`, `protected` modifiers matter

## Common Gotchas

1. **Arrays aren't C pointers**: `string *arr` is an array, not a pointer
2. **No semicolon after closing brace**: Unlike C++, no `;` after class/struct
3. **Mapping syntax**: Use `:` not `=>` or `=` in mappings
4. **Array literals**: Use `({ })` not `[]`
5. **String composition**: template literals for composed strings, `$N`/`$v`/`$o`
   tokens for action messages, adjacent literals for help text — not `+`
6. **Range indexing**: `str[<3..]` means "last 3 characters"
7. **varargs**: Optional parameters must use `varargs` keyword
8. **No main()**: Object entry points are lifecycle functions (`create`, `init`);
   commands are the exception — they do define `main()`
9. **`""` and `0.0` are TRUTHY in LPC**, unlike JS. Only `0`, null, and undefined
   are falsy — `if(!str)` does not catch an empty string. The `truthy()` /
   `falsy()` sefuns *do* treat `""` as falsy; pick deliberately.
10. **`0` is not `undefined`**: `nullp()` distinguishes them. Return
    `undefined` (from `global.h`) when a function has no answer, and document it
    as "returns undefined", not "returns 0".
11. **`typeof()` is overridden** to return `T_UNDEFINED` for null — the native
    version conflates it with `int`
12. **Reserved type words** (`buffer`, `function`, `class`, `mapping`, …) are
    never valid variable names
13. **Prefer `pointerp()`** over `arrayp()` — aliases, but `pointerp` is the
    project convention
14. **Guard functionals with `valid_function()`**, not bare `functionp()`, which
    is truthy on owner-destructed functionals
15. **Functional bindings**: FluffOS has functionals, not closures — nothing
    captures the enclosing scope. In `(: :)`, `$N` is a call-time positional
    argument while `$(EXPR)` is a value bound at creation — `$(2)` ≠ `$2`

## Verification

Before reporting LPC work as done, validate it compiles — the `fluffos_validate`
MCP tool and the LPC language server (`lpc_diagnostics`) are the sources of
truth. A clean compile is not proof of correct paths or behaviour; for anything
behavioural, verify in-game (see `/mud-telnet`).
